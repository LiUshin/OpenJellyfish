# Codex / Cursor 直接流式聊天

## 用户体验与接入边界

- 不再要求用户通过“创建运行会话”弹窗开始聊天。输入区选择模型，首次发送时自动关联供应商会话；打开旧聊天继续原上下文。
- 同一个连接允许逐轮选择模型。请求幂等包含显式模型，每轮记录 model 快照；授权、可用模型目录和账号代次在排队、启动及工具调用时重查。
- Codex 使用 `turn/start.model`，Cursor 使用同一个 ACP session 的 `session/set_model`。模型不变时跳过 Cursor 的设置请求。
- 使用供应商原生 harness 和会话存储。Jellyfish 不再把同一套指令拼进 Cursor 每一轮 prompt；首次成功之后由供应商上下文保留。失败的首轮仍会在重试时补上指令。
- 这是面向聊天的适配层，底层仍是官方 App Server / ACP 的有状态 Agent 协议，不声称是无状态 Chat Completions 接口。没有调用第三方订阅反向代理，也没有凭据转交。
- 文本增量、工具进度映射为 Jellyfish 现有 `StreamingMessage` 消息块。工具与文本顺序持久化；刷新、离开再返回可恢复。审批仍走原来的逐次审批入口。

## 客户端生命周期与延迟

客户端现在属于连接：登录完成和服务启动后预热，同一连接跨聊天复用单个官方客户端和独占凭据租约。每轮重新绑定 admin、工作区、原生 session、模型和工具回调。同一账号仍串行，不能用于不互信租户的隔离。

`JELLYFISH_RUNTIME_MAX_CLIENTS` 限制常驻进程数（默认等于并发数，上限 16）；连接显示预热中、可服务、执行中、等待容量或失败退避。取消、撤权、断连、探测模型和停服按范围回收。一个进程加载 32 个会话后回收，历史继续保留。`JELLYFISH_RUNTIME_KEEP_WARM=0` 可关闭预热，已迁移聊天继续使用连接 HOME 恢复。

首个文本块立即持久化并转发；后续仍按最多 60ms / 1024 字符合并，SSE 最长 50ms 查询间隔。没有等待完整回答后才发送。记录 `created_at`、`client_acquired_at`、`started_at`、`first_token_at` 和 `client_reused`，用于区分排队/准备和上游等待。

准备阶段不再反复初始化、登录、加载会话或重建 MCP。冷启动、换模型的网络请求以及供应商推理仍可能需要数秒；流式接口不等于即时首字。

## 工作区与副本

聊天协议不依赖副本。当前标准模式仍使用 actor/session 独立工作目录；只有显式导入的文档才复制，不是每轮复制整个项目。

按本次讨论，后续执行层可提供两种工作区：

1. **直接工作区**：可信团队使用当前 admin 的真实工作区，改动立即可见；需要接入既有工作区锁、文件变更通知和存储后端能力，不能把整个 users 根目录暴露给 CLI。
2. **副本工作区**：保留用于试跑、审查和回滚；确认后的产物再归档。

本次没有开启真实工作区写入。指定 `cwd` 只确定起始目录，不构成跨租户权限边界。不互信 admin 的执行隔离仍由未来 Docker / 集群后端提供；不因为换成 completion 风格接口而移除隔离。

## 验证

- Runtime 协议、权限、模型切换、复用、失效、容量、异常清理和消息块顺序：93 项通过。
- StorageService：22 项通过。前端 TypeScript / Vite 构建通过，仍有既有大 bundle 警告。
- 浏览器：普通输入框首次发送直接开始；同一 Codex 聊天从 GPT-5.6-Sol 切为 GPT-6-Astra，正确返回上一轮标记。

Cursor 三次复用使用相同 PID；同模型续聊准备耗时约 3ms，换模型仍需供应商设置请求约 3 秒。Codex 换模型复用同 PID，准备耗时约 2ms。结果差异包含模型和网络差异，不能视为严格性能基准或延迟保证。Cursor 冷启动样本从上一轮 16.4 秒波动到 22.4 秒，尚未解决所有冷启动成本。

Codex 原生 rollout 中的 turn_context.model 依次记录 GPT-5.6 / GPT-6；Cursor 原生 ACP 配置记录参数化的 GPT-5.6 变体，并核对发行包将它用于 requestedModel。两个连接换模型后都正确回忆原始标记。

复用后的 Cursor MCP 调用：先输出“开始工具验收”，请求并接受一次指定文档目录读取审批，两个工具进度事件完成，再输出“工具验收完成”。浏览器重新打开会话，文本/工具顺序和模型历史均恢复。

空闲租约到期后清理成功。Cursor 模型刷新曾返回一次 502；重试 9.5 秒成功，38 个模型。两个连接最终均 ready，无 recovery_required。未对该次供应商错误做自动重试或静默降级。


## 官方协议依据

- [Codex App Server](https://developers.openai.com/codex/app-server)：流式事件与逐轮模型覆盖。本机 0.154.0-alpha.6.2 的 `TurnStartParams` schema 同样包含 model。
- [Cursor ACP](https://cursor.com/docs/cli/acp)：session、流式更新和逐次权限请求。模型切换另对照本机官方 CLI 2026.09.15-d2fe57e 的 ACP 实现，设置后同步到 model manager 并用于 requestedModel。

## 原生能力和当前验收（2026-09-17）

旧 Codex rollout 与 Cursor SQLite 历史按精确会话 ID 迁移，不复制整个 HOME。图片通过原生视觉输入；普通附件写入当前聊天输入目录并提供显式路径。最多 5 个附件，单个 8MB、合计 12MB；读取校验 owner、路径和摘要。

Codex / Cursor 原生网页搜索、图片与文件输入均已真实验证；Codex 原生生图已生成并归档 PNG，Cursor 生图事件适配已实现，未完成真实生图验收。原生能力不可用时不静默改用其他付费供应商。

界面首段延迟拆分为准备和模型等待。Grok 33.9 秒样本中准备 26.9 秒、模型等待 7.0 秒；重复模型设置已避免，首个新进程仍强制设置一次以防 Cursor 返回的历史模型标签与实际执行模型不一致。后续短文本新聊天样本为 8.38 / 6.43 秒，续聊为 2.56 / 2.40 秒；不构成稳定性能保证，26.9 秒异常未再次复现。

当前 Runtime 测试 101 项通过，前端构建通过。附件和生图已通过 API 验证；生图前端最终视觉验收仍待补齐。上方会话级延迟表为早期历史样本。

# 管理员对话中的 Service 测试模式

## 使用方式

管理员在对话栏选择自己的一个 Service 并开启「测试模式」。草稿与已发布 Service 均可测试。从下一条消息开始，这个对话的用户输入交给所选 Service 处理，界面展示实际的 Service 回复。关闭测试模式后，后续消息重新交给管理员 Agent；此前的测试提问和 Service 回复仍留在当前管理员对话中，供 Agent 复盘和修改配置。

测试模式只属于管理员对话。Service 使用者的聊天页没有该开关。每个管理员对话独立保存当前选择；切换到另一个对话不会改变其模式。

## 执行边界

- 测试回合按 Service 当前保存的模型或 CLI core、Prompt 版本、文档与脚本范围、工具能力及独立会话上下文运行。管理员当前选择的模型、能力开关和项目 brief 不参与 Service 回合。草稿测试的是其当前保存配置，不能证明其未来发布时的配置仍相同。
- Service 测试上下文与管理员 Agent 的上下文分开。管理员对话里测试前的消息不能成为 Service 的历史；关闭模式后，管理员 Agent 可以看到测试记录。
- 测试消息保存在管理员对话，不能出现在真实使用者的 Service 记录或收件箱，也不能通过 Service Key 猜测会话 ID 来读取。测试模式不代替真实网页、API、微信渠道验收。
- 由于 `contact_admin` 会向管理员收件箱发出反馈，测试回合不应触发这项外部通知。界面需要明确说明此限制。其他 Service 工具仍受其发布范围和原有执行权限约束。
- 已开始的回合按开始时的模式完成；切换模式时不能将一个正在运行的回复拆给两种 Agent。Service 不可用或配置版本变化时，应明确报错并要求重新选择，不能静默回退到管理员 Agent。

## 数据与接口约定

管理员对话元数据保存 `test_service_id`。管理员可通过 `PATCH /api/conversations/{conversation_id}/test-mode` 提交 `{ "service_id": "svc_x" }` 开启，或 `{ "service_id": null }` 关闭；读取和列出对话时返回当前值。提交普通聊天消息时，服务器依据持久化的模式分流，无需客户端在消息请求中重复传入 Service ID。

测试所需的 Service 会话状态按管理员对话和 Service 分开存放，并标记为内部测试来源。Service 使用者记录、消息投递、收件箱查询必须排除这类状态。用量按实际执行的 core、模型计一次，归入管理员的 `admin_test` 渠道与当前管理员对话，不混入 Service 正式使用量。

## 验收要点

1. DeepAgents 和 CLI Service 均能从管理员聊天进入测试，输出及工具范围与对应 Service 一致。
2. 同一管理员对话的连续测试消息保留 Service 上下文；切换 Service 或重新开启时不会串用上一个 Service 的上下文。
3. 关闭后发送修改要求，管理员 Agent 能读到本次测试提问与回复；重新开启时历史管理员消息不会注入 Service。
4. 无权限的管理员不能启用别人的 Service；Service Key 与外部使用者均无法读取测试记录。
5. Service 记录、收件箱、消费者微信通知没有测试数据；失败状态和配置变化有明确提示。

# OpenJellyfish Runtime：PR 拆解与交付门槛

> 历史设计 / 阶段验收记录：文中的分支、角色与未实现项以记录当时为准。当前 v1.3.0 使用 [标准模式](runtime-standard-mode.md) 和 [主机超管控制台](superadmin-console.md)；早期验证结果不代表当前完整生产验收。

> 2026-09-17 更新：标准模式已改为独立主机 key 控制台，原 owner admin 绑定仅作历史阶段记录。当前入口与迁移规则见 [超管控制台](superadmin-console.md)。
2026-09-17 · PR 00–06 的本机可信团队标准模式已在 `codex/runtime-standard-pr06` 实现并验收；编号对应独立提交边界，尚未创建远端 PR。PR 01 中 Cloudflare、两个独立供应商身份、Cursor 登录仍未测。具体范围见 [运行说明](runtime-standard-mode.md) 与 [验收记录](runtime-pr06-evidence.md)。

## 1. 目标与范围

- 标准模式：超管连接账号，可授权指定可信 admin 使用；共享供应商额度，任务、应用会话、工作区与产物按执行者归属。
- 隔离模式：各 admin 自带 Codex / Cursor 账号，执行环境按需创建、空闲回收。
- 权限策略与执行后端分离：`access_mode=trusted_shared|tenant_isolated`；`execution_backend=local|docker|cloudflare`。ECS / EKS 后端以后按需求增加。
- 原有 DeepAgents 继续可用。先交付 Web 管理端，再交付公开消费者 Web 服务；微信、定时任务和语音另行迁移。
- 最大运行环境数在所有后端都有效，并同时受账号并发、租户配额、资源容量约束。云平台扩容不替代应用排队与预算。

## 2. 开发前基线（2026-09-16）

已核对 `app/runtime/`、`app/routes/runtime_pilot.py` 和相关文档：现有试验固定一个 admin、一个全局 `_pilot`，并用本地文件保存事件和会话。已有 stdio 适配、SSE 重放、审批、取消、文件导入和产物归档；不是分布式运行服务。

当前工作区还包含此前 scheduler 磁盘清理、关闭开关和部署改动。拆 PR 时按 diff hunk 分离；不整体提交 `app/main.py` / `.env.example` 等混合文件，不清理或覆盖用户工作。试验期间产生的登录缓存、环境值和运行数据不得进入版本控制。

## 3. PR 清单

### PR 00 — 收口已有 Codex 单管理员试验

- 范围：整理已存在的 adapter、试验路由/页面、探针、测试、启停文档；与原 scheduler 工作分离。
- 默认关闭试验开关；保留现有主聊天入口和 DeepAgents 行为。
- 验收：已有离线测试和前端构建；关闭开关后入口不可执行；记录已验证的真实文本与未验证的原生生图边界。
- 回退：关闭开关并重启；保留数据。此 PR 不声明多人可用。

### PR 01 — 提前验证共享身份与 Cloudflare 运行可行性

- 依赖：PR 00。产物是受控验证脚本、版本锁定及结论，默认不部署、不进入主服务启动链。
- 本机验证：超管一个供应商连接供两个 Jellyfish admin 顺序使用，独立 thread / 工作区 / 状态映射；验证登录缓存刷新、换绑检测和安全的凭据供给方式。
- Cloudflare 验证：真实 Codex 个人登录 → 推理/文件 → 目录保存 → 环境销毁/休眠 → 恢复 → 续话；两名 admin 使用不同供应商身份，验证不串凭据、会话和文件。
- 验证长任务脱离浏览器后继续、审批等待、取消、容器退出、流式输出和资源实际占用。记录冷启动、首 token、稳定输出延迟，分别测量。
- Cursor 只提前验证无头登录及身份目录是否可行，不在本 PR 实现完整适配器。
- 判定：分别给共享身份、Cloudflare Codex、Cursor 登录标记通过/受阻/未测。没有两个真实身份或云资源时保持未测，不能用同账号或 API Key 成功代替个人订阅登录成功。
- 若 Cloudflare 路径不可行，保留本机/Docker 开发；另立 ECS Fargate 验证，不自动引入 EKS。

### PR 02 — Owner 身份、权限策略和后端能力约束

- 依赖：PR 00；可在 PR 01 验证期间独立开发。
- 部署端显式绑定 owner，注册默认 admin，`/api/auth/me` 返回服务端角色与能力。
- `access_mode` 与 `execution_backend` 独立；不支持或尚未验收的组合拒绝启动/执行，不自动降级到 local。
- 校验主体权限后才能使用 unrestricted 工具策略；不让共享凭据把 admin 的执行权限提升成 owner。
- 验收：owner/admin × 标准/隔离矩阵；未配置 owner、客户端伪造角色、禁用后端和旧用户兼容。
- 默认不开放新连接功能；回退策略需保留角色绑定数据。

### PR 03 — 统一 Runtime 服务与本机执行后端

- 依赖：PR 00、02。
- 抽取 Run Service、RuntimeAdapter、ExecutionBackend；Codex 和 DeepAgents 使用统一运行入口，保留 DeepAgents 对外行为。
- 本机后端明确 start/stream/approve/cancel/terminate；后端能力包括文件物化、持久状态、出站策略及隔离级别。
- 持久 run_id、事件序号、request_id 幂等、终态与待审批状态；先限制单调度进程，不伪装已支持多副本。
- 定义有界持久队列、每账号/每 admin/全局上限；起步每共享连接并发 1。重启后的未知运行标记待恢复/失败，不自动重放外部副作用。
- 验收：断开浏览器、事件重放、重复请求、取消与子进程退出、未知审批拒绝；DeepAgents 的代表性聊天/工具流程回归。

### PR 04 — 超管 Codex 连接管理，接入设置页

- 依赖：PR 01 共享身份结论、02、03。
- 持久 RuntimeProfile、LoginAttempt、auth_generation；凭据引用与应用业务数据分开。
- `/settings/general` 增加本人连接、登录挑战、状态、模型列表、重新登录/断开；无须依赖单独试验台来管理账号。
- 账号代次变化使旧运行绑定失效；协调刷新写入，清理过期登录尝试，日志与接口不暴露凭据。
- 验收：取消/过期/重复登录、旧回调到达、换账号、断开时有任务、非 owner 在标准模式请求登录被拒绝。
- 本 PR 只开放超管个人连接；不启用共享使用。

### PR 05 — 可信 admin 授权与共享 Codex 闭环

- 依赖：PR 03、04。
- RuntimeGrant、连接列表的 personal/owner_shared、可管理/可使用分离；新增 admin 默认未授权。
- 超管设置页授权/撤销指定 admin；admin 看到团队连接及获准模型，没有换绑/断开入口。
- 凭据所有者、任务发起者、数据归属分别绑定；共享账号排队，按 admin 归因用量。入队/启动/恢复/审批重新检查授权版本。
- 撤销时阻止新运行，取消队列与运行任务，确认退出；换账号后授权必须重新确认。账号失效/额度不足不切换他人账号或付费 API。
- 验收：两 admin 各自会话、审批、事件、产物；交叉读取/审批被拒绝；撤销与启动竞态；一账号配额不会因多人共享而被放大。
- 标准模式只对可信团队开放，未声明 OS 租户隔离。

### PR 06 — 主聊天接入与引擎能力贯通

- 依赖：PR 03–05。
- 主聊天创建会话时固定 runtime / connection / model / image_mode；设置默认值只影响新会话；旧无 runtime 字段的会话继续 DeepAgents。
- 将现有对话、流式输出、审批、停止、文档导入、产物预览接入统一运行服务。
- 为替代引擎提供受作用域约束的业务工具入口；系统提示、记忆读取/写入和服务文档分别做最小实际验证，明确不支持的能力，不宣称自动拥有全部 DeepAgents 行为。
- 生图能力独立开关：原生输出验证真实文件、来源与归档；选定供应商时才调用该供应商，不静默付费回退。
- 验收：owner 和获授权 admin 在主聊天完成真实多轮文本、一次审批、文档产物；真实生图未通过时保持能力关闭。
- 测首 token 和连续输出；仅对已定位的 fsync / 轮询瓶颈做改动，不能牺牲审批和终态的持久性。
- **里程碑 A：可信团队标准模式可以内部使用。**

### PR 07 — 可迁移工作区与多副本任务状态

- 依赖：PR 03；接口取舍使用 PR 01 的实际结果。
- 分开存放：加密凭据、业务会话/事件、工作区检查点、产物。抽象本地与远端存储，登录缓存不进入普通文档备份/下载。
- 为多调度副本采用可事务更新的共享状态实现：任务领取租约、心跳、版本化执行令牌、幂等归档、事件重放、按租户检查点和排队/运行配额。
- 远端状态实现必须具体落地并验证；不能将本地文件锁或内存计数器当分布式锁。实现前记录选定存储及其原子操作依据。
- 恢复前确认旧执行已退出或已隔离；仅 TTL 到期不能证明旧进程停止。禁止两个环境同时写同一工作区；不能安全续跑时显式失败。
- 验收：两调度副本争抢同任务、租约过期、迟到回调、进程崩溃、凭据刷新冲突、事件断流、部分上传、取消/恢复竞态。
- **这是云端扩容前置条件，不能留到发布前补。**

### PR 08 — 可选 Docker 隔离后端

- 依赖：PR 02–04、07。
- Broker、固定镜像、租户私有挂载、资源/网络策略、按需创建、保温回收、完整进程清理；主应用默认包不增加 Docker 必装项。
- 隔离模式下开放各 admin 自己登录 Codex；执行对象包含 tenant/profile generation/scope，不将带数据的容器分配给其他租户。
- 同部署内 DeepAgents 脚本、安装包等其他不可信执行入口也须隔离或关闭；消费者不能获得 admin 全工作区。
- 验收：跨租户路径/进程/网络访问、宿主及元数据访问、资源耗尽、恶意子进程残留、故障时不回落宿主机。
- 先实验开关；普通 runc 容器启动成功不等于严格隔离通过。未完成加固验收时不得对不可信用户开放。

### PR 09 — Cloudflare 执行后端与弹性调度

- 依赖：PR 01 Cloudflare 验证通过、02–04、07；无需依赖 Docker 后端实现完成。
- Worker 受认证执行接口、DO 协调、Container/Sandbox 执行，R2 存检查点/产物；现有 Jellyfish 主服务可以保留 Python。
- 复用统一运行协议；将环境按实例 ID 创建、回收；有界队列、租户公平性、全局/账号上限和原子容量领取。
- 多租户密钥不放成所有沙箱共享的环境变量；执行控制端不能把任意客户端路径、命令或 sandbox ID 当成授权。
- 活跃任务/审批与休眠策略协调；HTTP/SSE 断开不触发重跑。区分正常释放、平台重启、版本更新和任务失败。
- 验收：两租户真实登录和并发、销毁恢复、取消、重连；目标负载下的排队时间、冷启动、首 token、内存和保温成本；平台限额耗尽时可控排队/拒绝。
- 以 PR 01 固定的 SDK/API 版本为基线，单独记录升级策略。通过全部边界验收后才开启受控租户试用。
- **里程碑 B：至少一个经过验收的隔离后端支持多 admin 自带账号。**

### PR 10 — Cursor CLI 适配器

- 依赖：PR 01 Cursor 登录结论、03、04、06；某隔离后端可用时再验收该后端。
- 实现 Cursor 登录/状态/退出、ACP 消息/工具/审批/取消/恢复映射；模型和生图按实际能力返回。
- 使用相同 Profile、Grant、RunBinding 和执行后端契约，不再新增一套租户调度或设置页。
- 验收：本机真实多轮、取消、审批、产物、账号切换；每个对外支持的隔离后端都单独实测。仅 Codex 通过的后端不得自动标记 Cursor 可用。
- Cursor 能力独立发布，不阻塞 Codex 标准模式里程碑。

### PR 11 — 消费者 Web 服务与 ToC 发布门槛

- 依赖：PR 06、07，以及 PR 08/09 中至少一个严格隔离验收通过的后端；Cursor 是否纳入发布取决于 PR 10 的验证。
- 公开服务使用独立的 ServiceExecutionPolicy：服务所有者、调用者、允许文档/工具、计费连接、会话和工作区分别绑定。
- 公共消费者请求不得直接复用 admin 的完整可写 HOME、原生 shell 权限或全量文档；按服务/消费者作用域物化最小资源。
- 云部署清除单机事实源：身份、授权、应用数据与运行状态的共享存储；校验所有启用入口。数据库等主服务扩容也需独立容量指标，不能只扩沙箱。
- 补齐限流/预算、运行与存储留存、凭据撤销、滚动更新、备份恢复、模式迁移、观测和故障处置；禁止日志泄露凭据。
- 验收：消费者之间、消费者与 admin 之间的越权；外部副作用重复提交；饱和排队、取消风暴、平台重启、账号掉线、升级回退与代表性目标负载。
- 先发布带开关的受控范围；以实测容量、延迟、恢复行为与成本决定开放规模，不给未经测量的并发承诺。
- **里程碑 C：公开消费者 Web 服务达到明确的发布门槛。微信、调度、语音继续保持原路径或关闭新引擎能力，后续各自成 PR。**

## 4. 依赖与拆分原则

```text
00 试验基线 ──→ 01 可行性验证 ───────────────────┐
       └──→ 02 角色策略 → 03 运行服务 → 04 连接 → 05 共享 → 06 主聊天
                              └──→ 07 持久化与租约 ──→ 08 Docker
                                                      └→ 09 Cloudflare
                         01/03/04/06 ──→ 10 Cursor
                         06/07 + 已验收隔离后端 ──→ 11 ToC Web
```

- 编号表达评审边界，不要求全部串行。PR 01 与 02 可独立推进；07 可早于主聊天交付；08 与 09 各实现同一后端接口，不互相依赖。
- 每个 PR 有明确触发场景、行为变化、验证证据和回退方式；未通过的能力保持关闭。
- schema 先做向后兼容扩展；回退关闭新任务入口并等待/终止旧执行，不删除凭据、会话或产物，不跨供应商自动重跑。
- 表内某个 PR 若超出可评审范围，按一个可验证行为继续拆分。例如 PR 06 可拆为“主聊天接入”和“业务工具/生图能力”，PR 07 可拆为“工作区持久化”和“分布式运行状态”；不能为了固定 PR 数量凑大包。
- 不在上述批次内建设 EKS。只有出现明确的资源、网络、运行时或已有 Kubernetes 运维需求时，另立 AWS 后端 PR，优先对照 ECS Fargate 与 EKS 的实际需求和成本。

## 5. 本次之后的第一步

先整理 PR 00 的改动清单和验证基线，再开始 PR 01 的最小实验与 PR 02 的 owner/策略基础。真实供应商登录由对应账号持有人完成；需要云账号、配额或另一名测试账号时，在实验真正依赖它时提出具体需求。

本计划没有创建云资源、购买服务、登录新账号、提交 commit、创建远端 PR 或启动新实现。
